# 后端错误国际化设计规范

## 1. 目标

本规范定义 FluxTerm 后端错误的国际化契约，确保 Rust 后端可以提供稳定、可翻译的错误语义，前端根据当前语言完成本地化展示。

后端错误不应依赖中文硬编码作为主要展示路径。`message` 统一使用英文兜底文本，面向用户展示的错误应优先提供 `messageKey`。

## 2. 错误契约

后端面向前端返回的标准错误结构应包含以下字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `code` | `string` | 稳定错误码，用于日志、分类、兼容映射和粗粒度处理 |
| `message` | `string` | 英文兜底可读文本，不作为国际化主路径 |
| `messageKey` | `string?` | 前端 i18n 翻译键，面向用户展示时优先使用 |
| `messageVars` | `object?` | 翻译变量，仅承载简单可序列化值 |
| `details` | `string?` | 调试细节或底层错误信息，不直接替代用户提示 |

`code` 和 `message` 为兼容字段，应长期保留。`messageKey` 和 `messageVars` 是新的用户展示契约。

## 3. 前端翻译规则

前端收到错误后，应按以下优先级生成展示文本：

1. 如果存在 `messageKey`，使用 `messageKey` 和 `messageVars` 翻译。
2. 如果没有 `messageKey`，尝试根据 `code` 映射到历史翻译键。
3. 如果 `message` 本身是历史翻译键，按兼容逻辑翻译。
4. 如果以上都失败，展示原始 `message`。

前端不应通过解析自然语言判断错误类型，也不应把 `details` 当作用户展示文案。

## 4. 后端实现规则

新增后端错误时应遵循以下规则：

1. 必须提供稳定 `code`。
2. 面向用户展示的错误必须提供 `messageKey`。
3. `message` 应写成英文可读兜底文本，不能使用中文，也不能只放翻译键。
4. `details` 只用于底层错误、调试信息或日志补充。
5. `messageVars` 只放字符串、数字、布尔值或空值等简单变量。

错误码应使用下划线风格，例如 `ssh_auth_failed`。翻译键应使用点号小写分组风格，例如 `error.ssh.auth.rejected`。

## 5. 迁移策略

后端错误国际化按模块分批迁移，不一次性修改所有硬编码错误。

第一批迁移范围：

1. 扩展 `EngineError`，增加 `messageKey` 和 `messageVars`。
2. 扩展前端 `AppError` 和错误翻译流程。
3. 迁移 SSH 认证相关错误。

后续迁移建议顺序：

1. SFTP 与远端编辑错误。
2. RDP 错误。
3. AI 配置与请求错误。
4. local shell 与本地文件错误。
5. 代理、隧道、资源监控和配置读写错误。

每批迁移都应保持旧字段兼容，并优先覆盖用户可见、高频和容易误导的错误。

## 6. 禁止事项

1. 不要把中文硬编码作为前端国际化主路径。
2. 不要让前端通过包含判断、正则或自然语言文本识别错误类型。
3. 不要把底层库错误直接暴露为用户主提示。
4. 不要删除 `code`、`message`、`details` 等现有兼容字段。
5. 不要在一个提交中混合大量模块迁移和无关重构。
