# RDP 远端音频播放设计

## 目标

FluxTerm 在建立 RDP 会话时默认声明远端音频能力，将远端系统声音播放到本机，并提供会话级静音控制。音频异常只影响声音，不中断画面、输入、缩放或剪贴板。

本功能不包含麦克风回传、音量调节、输出设备选择和 Profile 级音频开关。

## 协议与播放链路

连接器同时注册 `rdpsnd` 和 `rdpdr` 静态通道。`rdpdr` 使用不声明任何设备的空后端，仅满足 Windows 服务端建立 Remote Audio 设备所需的通道组合，不启用磁盘、打印机或智能卡重定向。

IronRDP 0.8 负责 `rdpsnd` 协商、训练、数据确认和格式重协商。FluxTerm 的播放后端只声明 44.1 kHz、16-bit、双声道 PCM，通过 CPAL 0.17 输出到系统默认设备。

播放缓冲最多保留两秒数据。缓冲溢出时丢弃最旧数据，避免音频延迟持续累积。静音时播放回调立即输出静音并清空缓冲，取消静音后只播放最新收到的数据。

## 状态与控制

会话快照包含：

- `audioEnabled`：当前版本固定为 `true`。
- `audioMuted`：会话级静音状态。
- `audioState`：`idle`、`negotiating`、`playing`、`muted` 或 `error`。

播放线程通过桥接事件 `audio-state` 上报状态。RDP 连接进入活动阶段后状态为 `idle`；收到音频包后进入 `playing`，连续 750 毫秒没有收到新音频包时回到 `idle`。因此状态描述的是远端音频数据活动，而不是 CPAL stream 是否仍保持打开。

前端静音命令只修改当前活动会话，不影响其他 RDP 标签。`audioMuted` 覆盖显示为 `muted`，会话管理器同时保存未静音时的底层活动状态；取消静音后恢复最新的 `idle`、`playing` 或 `error`，不重新猜测为协商中。播放设备初始化失败时状态进入 `error`，错误信息保留在音频状态中，不升级为会话连接错误。

## 生命周期

断开会话时先向协议任务发送退出命令。活动阶段发送 RDP `ShutdownRequest` 后继续处理网络数据，等待服务端的关闭响应以及 IronRDP 输出最终 `Terminate`，再销毁 `rdpsnd`。播放后端随后停止 CPAL stream、唤醒并回收音频线程。只有这些步骤完成后才从会话管理器删除记录。

活动阶段等待关闭响应的上限为四秒，超时后主动结束传输层；会话管理器等待整个运行时退出的上限为五秒，超时后记录结构化日志并中止任务，避免关闭标签或窗口无限等待。该顺序用于防止前一会话仍占用远端音频端点或本机音频设备时创建下一会话。

## 验证重点

1. 对同一主机连续连接和断开至少三轮，每轮都能创建 Remote Audio 并播放。
2. 静音立即生效，取消静音后不回放静音期间积压的数据。
3. 服务端重新协商音频格式后能够继续播放。
4. 多会话静音状态互不影响。
5. 本机没有默认输出设备时，画面和输入仍可正常使用。
